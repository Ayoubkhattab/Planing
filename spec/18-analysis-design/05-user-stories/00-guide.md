# قصص المستخدم — الدليل

قصة مستخدم لكل عملية في النظام، مولَّدة من المواصفات المعتمدة، مصنفة حسب **نوع العملية** (إنشاء، تعديل، سير عمل، حذف/إنهاء، جلب، نظام) و**فئة المجال** (أساسية، تحليل، تقارير ومنتجات، تكامل، حوكمة وأمن). كل قصة تحيل إلى مصادرها، فلا تضيف سلوكًا غير موجود في المواصفات.

**المجموع: 739 قصة** = 477 أمرًا (قصة لكل `CMD-*`) + 133 استعلامًا (قصة لكل `QRY-*`) + 129 قاعدة انتقال تلقائي (`SYS:`) تغطي 175 انتقالًا من حالة إلى حالة في 56 Aggregate. الفرق عن التقدير الأولي في الفهرس (~785) أن قاعدة `SYS:` الواحدة قد تنطلق من عدة حالات، فتُكتب قصة واحدة لها.

داخل كل ملف: ملخص حسب نوع العملية، ثم لكل Aggregate: قصص أوامره، ثم قصص انتقالاته التلقائية، ثم قصص استعلاماته. الاستعلامات التي لا تخص Aggregate واحدًا في قسم أخير «استعلامات عابرة للـAggregates».

## 2. معرّف القصة

| الشكل | المثال | المصدر |
|---|---|---|
| `US-BCnn-<الأمر بلا CMD->` | `US-BC04-TASK-ASSIGN` | `CMD-TASK-ASSIGN` |
| `US-BCnn-Q-<الاستعلام بلا QRY->` | `US-BC04-Q-TASK-LIST` | `QRY-TASK-LIST` |
| `US-BCnn-S-<الـAggregate بلا AGG->-nn` | `US-BC04-S-TASK-01` | القاعدة `SYS:` رقم nn في جدول انتقالات `AGG-TASK` بترتيبه |

المعرّف ثابت ما دام المصدر ثابتًا؛ إعادة ترتيب جدول الانتقالات تغيّر أرقام قصص `SYS:` فقط.

## 3. قالب القصة

```text
#### <المعرّف> — <العملية بالعربية>
| النوع | الفئة | الفاعل | الواجهة | السياسة |
القصة:    بصفتي <الفاعل>، أريد <العملية>، لكي <الغرض>
الشروط المسبقة: الحالات المسموح منها + شروط الانتقال (Guards)
المدخلات:  حقول الحمولة (! = إلزامي) + Idempotency-Key + If-Match لغير الإنشاء
المخرجات:  الحالة الجديدة، الحدث، ResourceRef
الصلاحية:  موضوع السياسة، الشروط، فصل المهام، الالتزامات
الربط:     CMD/QRY، AGG، REQ، UC
ضوابط النوع والفئة: معرّفات من §5 و§6
معايير القبول: Gherkin — سيناريو نجاح + Scenario Outline بكل رموز الخطأ
```

| الغرض | «الغرض» في ملف الـAggregate؛ وللاستعلام نص أول متطلب مرتبط | |

| الشروط المسبقة | جدول الانتقالات في ملف الـAggregate (أعمدة «من» و«الشرط») | «أي حالة غير نهائية» تُفك إلى قائمة الحالات |
| المدخلات | عمود «الحمولة» في كتالوج الأوامر | |
| المخرجات | أعمدة «إلى» و«الحدث» في جدول الانتقالات | `(بلا تغيير)` = أمر لا يغيّر الحالة |
| الصلاحية | سياسة الأمر: `subject`، `context_conditions`، `segregation_of_duties`، `obligations` | |

## 4. تصنيف العملية

## 5. ضوابط القبول حسب نوع العملية

كل قصة تحمل معرّف ضابط نوعها. الضابط قائمة أسئلة يجب أن يجيب عنها التنفيذ واختباراته، **إضافة** إلى سيناريوهات Gherkin في القصة.

### C-CRE — إنشاء
1. المعرّف ULID والـURN بالصيغة `urn:<namespace>:<type>:<ulid>` (ADR-P13). من يولّد المعرّف في الأوامر المسموحة دون اتصال (`x-offline-capable`) يُحسم في `20-integration-design.md` **[Needs Review]**.
2. كل حقل إلزامي (`!`) مفقود → `VALIDATION_FAILED` (400)، ولا يُنشأ شيء.
3. التكرار بنفس `Idempotency-Key` ونفس الحمولة يعيد نفس `ResourceRef` بلا إنشاء ثانٍ؛ مع حمولة مختلفة → `IDEMPOTENCY_KEY_REUSED` (422).
4. الاستجابة 201 مع `ResourceRef` (`urn`، `id`، `version = 1`، `state`).
5. `tenant_id` يؤخذ من سياق الأمن لا من الحمولة (ADR-P04)؛ العلامة الأمنية (`label`) جزء من مدخلات قرار السياسة (ADR-P06).
6. تُكتب الحالة وسجل `_history` والحدث وسجل التدقيق في معاملة واحدة (FIT-04).

### C-UPD — تعديل (لا يغيّر الحالة)
1. `If-Match` إلزامي؛ عدم المطابقة → `VERSION_CONFLICT` (409)، ولا يُفحص إلا بعد التخويل الكامل (ADR-P17، الخطوة 7).
2. الإصدار يزيد بواحد ويُحفظ إصدار غير قابل للتعديل في `_history`.
3. ما يُجمَّد بعد حالة معينة (مثل معايير الإكمال بعد `ASSIGNED`) يُرفض بخطأ الشرط المذكور في القصة.
4. الحالات التي لا يُقبل منها الأمر (خلايا ✗ في المصفوفة) → `*_INVALID_STATE_TRANSITION` (409).
5. الحدث يحمل ما تغيّر (`changes`) لا الكيان كله.

### C-WF — سير عمل (ينقل الحالة)
1. الانتقال من حالة غير مسموحة → `*_INVALID_STATE_TRANSITION` (409)، والحالة لا تتغير.
2. فصل المهام يُقيَّم بعد تحميل المورد (ADR-P17، الخطوة 5)؛ المخالفة → `SEGREGATION_OF_DUTIES`.
3. الالتزامات قبل التنفيذ (MFA، موافقة) تُستوفى قبل الانتقال، وإلا يُرفض الأمر ولا يُنفَّذ شيء.
4. الانتقال إلى حالة ينتظرها طرف آخر يُطلق حدثًا يستهلكه الإشعار حيث يذكر كتالوج الأحداث ذلك.
5. السبب إلزامي حيث يذكر الشرط «reason» → `REASON_REQUIRED`.

### C-DEL — حذف / إنهاء
1. **لا حذف فعلي للسجلات.** الإنهاء انتقال إلى حالة نهائية (`CANCELLED`، `RETIRED`، `CLOSED`…) يحفظ التاريخ كاملًا.
2. المحو والإتلاف (`ERASE`، `DISPOSE`) يتمّان بإتلاف مفتاح التشفير (ADR-P08) ويتركان سجل إتلاف (tombstone)، ويُمنعان تحت تجميد قانوني.
3. الحالة النهائية لا تقبل أي أمر يغيّر الحالة بعدها.
4. السبب إلزامي في كل إنهاء يذكره الشرط.
5. الإسقاطات تستهلك حدث الإنهاء وتحدّث حالة المورد فيها، فلا يظهر في البحث والقوائم كمورد نشط.

### C-READ — جلب / استعلام
1. قرار السياسة قبل أي قراءة (FIT-03)؛ `allowed_scope` يُطبَّق قبل العدّ والترتيب والترقيم.
2. المورد غير المرئي يُعاد بنفس شكل المورد غير الموجود (404)، ولا يكشف العدد أو الاقتراحات أو الأوجه وجوده.
3. كل عنصر مُعاد يُعاد فحصه: إصدار الأمن للموضوع وفحص العلامة `LabelCheck` مجمّعًا لكل صفحة (CR-47).
4. القوائم تُرقَّم بمؤشر (`cursor`، `limit ≤ 200`) لا بالإزاحة (FIT-13).
5. الاستعلام بأثر رجعي (`valid_at`، `known_at`) يعيد ما كان معروفًا حينها لا ما يُعرف الآن.

### C-SYS — عملية نظام
1. تدخل عبر نفس خط الأوامر بهوية عبء عمل (workload identity)، بنفس الثوابت وشروط الانتقال.
2. عدم التكرار: إعادة المحفِّز نفسه لا تُنتج انتقالًا ثانيًا (مفتاح عدم التكرار مشتق من المحفِّز).
3. نوع المحفِّز يحدد آلية التشغيل: **زمني** (مجدول يفحص دوريًا)، **شرطي** (بعد أمر يغيّر الشرط)، **مدفوع بحدث** (مستهلك حدث عبر inbox)، **مدفوع بعامل** (نتيجة عمل عامل خلفي) — `11-hexagonal-reference.md` §4.
4. الفشل يُعاد بمحاولات محدودة ثم يُسجَّل ويُنبَّه عليه، ولا يُسقَط بصمت **[Derived]**؛ سياسة إعادة المحاولة في `15-event-design.md` §5.
5. سيناريو القبول موجود في ملف قبول الـAggregate (CR-72).

## 6. ضوابط القبول حسب فئة المجال

### K-CORE — أساسية
لا ضوابط إضافية على ضوابط النوع.

### K-ANL — تحليل
1. كل نتيجة تحليلية تحيل إلى أدلتها ومصادرها (النسب — BRL-001)، ومعها مستوى الثقة وطريقة التحليل وإصدارها.
2. التشغيل قابل للإعادة: نفس المدخلات بإصداراتها ونفس الطريقة تعطي نفس النتيجة، وإلا تُسجَّل أسباب الاختلاف.
3. ما يقترحه الذكاء الاصطناعي أو القواعد يبقى مقترحًا حتى يقبله محلل؛ لا كتابة مباشرة في T1.
4. العلامة الأمنية للنتيجة لا تقل عن أعلى علامة في مدخلاتها.

### K-RPT — تقارير ومنتجات
1. المنتج يحمل علامته الأمنية على كل صفحة وتصدير، وعلامة مائية باسم المستلم حيث تنص السياسة.
2. الاعتماد والنشر بغير المؤلف (فصل المهام).
3. المحتوى المستبعد بسبب الصلاحية يُسجَّل استبعاده، لا يُحذف بصمت.
4. التوزيع يُدقَّق لكل مستلم، والسحب يُبلَّغ لكل من استلم.

### K-INT — تكامل
1. كل ما يدخل يحمل مصدره وموثوقيته ومعرّفه الخارجي، وما يفشل التحقق يذهب إلى الحجر لا إلى البيانات.
2. التحويل عبر طبقة مضادة للفساد (ACL) إلى نموذج المجال؛ لا تتسرب أنواع النظام الخارجي إلى الداخل.
3. المزامنة الميدانية لا تستخدم «آخر كتابة تفوز» لبيانات T1/T2 (FIT-15)؛ التعارض يُسجَّل ويُحل.
4. إعادة المعالجة لا تنشئ تكرارًا (عدم التكرار بالمعرّف الخارجي).

### K-GOV — حوكمة وأمن
1. تغيير الصلاحيات أو التصنيف يرفع إصدار الأمن للموضوع ويُبث على قناة `security.versions` ذات الأولوية.
2. التغيير الحساس يتطلب شخصًا ثانيًا حيث تنص السياسة، ومصادقة متعددة العوامل عند الحاجة.
3. كل تغيير يُدقَّق بما قبله وما بعده، وسجل التدقيق غير قابل للتعديل.
4. فشل محرك السياسات يعني الرفض (FIT-16).
